# 演示步骤与数据

本目录提供客户行为、市场表现两条完整演示：每条三轮普通分析、一轮显式最终报告，以及原始业务CSV和第三轮补充附件。数据全部合成，种子 `20260901`，仅含Windows/macOS电脑。

## 1. 准备和登录

1. 打开交付入口 **https://192.168.10.22**，点击“通过认证中心登录”。
2. 使用项目根目录 `.run/compose-package/.secrets/demo-accounts.json` 中的 `analyst_demo`，身份选“分析用户”。开发入口 `https://localhost:8443` 使用根目录 `.secrets/demo-accounts.json` 中的密码；两套密码不同。
3. 确认管理员已初始化六个数据源，并发布有效模型配置。缺数据时按 [README的数据初始化](../../README.md#数据初始化与模型配置) 准备；本目录CSV无需在工作台逐个上传，主数据从绑定的PostgreSQL源查询。
4. 演示会调用真实模型并产生费用；不要同时运行其他会修改配置或重启服务的任务。

每次选择一个新会话和正确数据源；首次发送后数据源锁定，换场景需要另建会话。每轮等待成功后再追问。失败重试会新增用量，不把失败轮次计入成功演示。

共同口径：**Asia/Shanghai，基期2026-09-01至09-07，分析期2026-09-08至09-14**。建议保留在每轮问题开头。以下代码块仅是提问，不包含基准答案。

## 2. 客户行为分析

新建会话并选择“客户行为分析”，可命名为“客户行为演示”。

### 第一轮：整体漏斗

保持本轮附件为空，发送：

```text
基期2026-09-01至09-07，分析期2026-09-08至09-14，时区Asia/Shanghai。
为什么本期客户下单转化下降？比较两周访问、加购、有效下单的严格漏斗，列明口径和查询证据。
每周独立筛选事件，再计算该周每用户首次访问；同一用户可以分别进入两周漏斗，不能用两周全局首次访问时间归期。
同用户同一期内必须先访问、后加购、再paid/completed下单，步骤时间严格递增。按该周首次访问设备互斥归属，同时间首次访问按event_id确定；后续切换设备不重复分组。
仅查询所需聚合，保持结果简洁，区分已证实事实、推断和缺口。
```

### 第二轮：电脑设备拆解

第一轮成功后继续在同一会话发送：

```text
沿用基期2026-09-01至09-07、分析期2026-09-08至09-14和Asia/Shanghai时区。
仅按Windows与macOS电脑拆解同口径严格漏斗，哪个环节变化最大？核对分组之和与整体，并说明分组贡献。
```

### 第三轮：补充错误资料

下载 [client_error_summary.csv](client_error_summary.csv)，在会话附件面板上传，等待解析成功，**显式勾选作为本轮附件**，再发送：

```text
沿用此前两期和口径。结合本轮新增错误汇总更新判断，说明相比前两轮结论发生了什么变化。
区分已证实事实与待验证解释，错误次数不能当作受影响用户数、故障率或因果证明。
列出缺失数据，并给出至少两项可执行排查建议及验证方式。
```

## 3. 市场表现分析

另建会话并选择“市场表现分析”，可命名为“市场表现演示”。

### 第一轮：整体收入与投放

保持本轮附件为空，发送：

```text
基期2026-09-01至09-07，分析期2026-09-08至09-14，时区Asia/Shanghai。
为什么本期销售收入下降，投放效率是否同步恶化？比较两周有效支付收入、订单及投放，核对明细与销售汇总。
只计paid/completed，按paid_at归期，不能用created_at代替；按订单粒度去重。投放独立聚合后关联，缺支付时间的订单单列质量缺口，保留未归因及无订单投放渠道。
仅查询必要聚合，区分事实、推断和缺失数据。
```

### 第二轮：渠道贡献

第一轮成功后在同一会话发送：

```text
沿用基期2026-09-01至09-07、分析期2026-09-08至09-14和Asia/Shanghai时区。
分渠道拆解收入变化，比较ROAS和获单成本，核对渠道之和与整体。明确关联使用的期间和渠道粒度，避免关联放大。
查询出现重复行时先复核查询关联；未经直接核验，不把查询重复写成源表重复。
```

### 第三轮：补充投放记录

下载 [promotion_calendar.md](promotion_calendar.md)，在附件面板上传，等解析成功后**显式选择本轮使用**，再发送：

```text
沿用此前两期和口径。结合本轮新增投放记录更新判断，说明新增资料如何改变或补充结论。
区分事实、可能解释和缺失数据，不把时间重合写成因果；提出至少两项渠道排查或小规模验证建议，注明衡量指标、证据和局限。
```

## 4. 生成、导出和复核

两个场景分别完成前三轮后：

1. 点击输入区的“生成最终报告”进入最终报告模式，确认固定范围包含该会话前三轮成功分析，本轮不携带新附件。
2. 输入汇总要求并再次点击提交按钮“生成最终报告”：

   ```text
   汇总前三轮成功分析，覆盖总体变化、分组拆解、新增资料及结论变化、未验证事项。
   保留至少一条数据库证据和一条新增附件证据，列明口径、缺口和至少两项行动建议。
   不重新取数，不把相关性当作因果，纠正前轮未经证实的判断。
   ```

3. 确认结果包含问题定义、关键指标、证据列表、分析结论、待补充数据和下一步建议；展开证据核对SQL/文件名及位置。
4. 分别生成并下载Markdown、HTML；生成状态与分析状态独立，失败可按格式重试。HTML可离线打开。
5. 退出后重新登录，打开历史并重新下载，确认正文与文件一致。刷新、重连不应重复提交分析。

已有交付演示会话为“客户行为分析 · 电脑端演示”（会话3，最终任务8）和“市场表现分析 · 电脑端演示”（会话5，最终任务16）；这些是历史实例记录，不是新建会话时要求填写的ID。实际证据见 [交付收尾报告](../../docs/验收报告/交付收尾/20261024-032617-desktop/验收报告.md)。

## 5. 核对基准（只用于验收）

这些值用于操作人员独立核对，不复制到模型提问或运行逻辑中。

### 客户行为

| 设备 | 基期访问 | 分析期访问 | 基期加购 | 分析期加购 | 基期有效下单 | 分析期有效下单 |
| --- | --- | --- | --- | --- | --- | --- |
| Windows | 600 | 600 | 300 | 180 | 120 | 60 |
| macOS | 400 | 400 | 200 | 200 | 80 | 80 |
| 整体 | 1000 | 1000 | 500 | 380 | 200 | 140 |

整体访问→有效下单20%→14%，下降6个百分点、相对下降30%；Windows下单减少60人，贡献全部净下降。错误汇总中Windows10→70次、macOS5→5次，属于相关线索，不能证明错误导致转化下降。

### 市场表现

| 指标 | 基期 | 分析期 |
| --- | --- | --- |
| 有效支付收入（元） | 20000 | 16000 |
| 有效支付订单（单） | 200 | 160 |
| 投放费用（元） | 2000 | 2500 |
| ROAS（收入/投放） | 10 | 6.4 |
| 获单成本（元/单） | 10 | 15.625 |

A渠道两期均为100单、10000元收入、1000元投放。B渠道100→60单、10000→6000元收入、1000→1500元投放，ROAS10→4、获单成本10→25。B贡献全部4000元收入下降；投放记录只是时间重合证据。本演示不含退款，不能声称已计算净收入。
