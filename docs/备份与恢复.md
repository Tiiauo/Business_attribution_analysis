## 实际恢复演练

`--restore-check` 不是只检查压缩包：它创建随机 `ba-restore-<12位UUID>` 网络和四个新卷，不发布任何端口，解包文件、启动独立PostgreSQL并执行 `cluster.sql`。恢复库时区为Asia/Shanghai，与源实例一致。随后逐表核对行数及全部行内容SHA-256、角色摘要、应用/Caddy/密钥文件摘要，解密配置凭证，并逐个登录六个只读数据源。原实例不参与覆盖。

演练结束仅删除本次UUID资源，备份、当前交付项目和历史实例卷保留。`restore-check.json` 记录结果；`manifest.json` 和 `restore-observed.json` 含文件清单及私密状态摘要，保留在受限目录。失败不能作为通过，源服务会在备份导出阶段的finally中重新启动。

## 故障恢复步骤

1. 选定完整备份，先在隔离环境运行恢复核验；不要覆盖唯一现存副本。若VM备份目录仍在，可在Python中通过 `runpy.run_path('scripts/backup-compose.py')['restore_check'](远端目录, Path(本机受限证据目录))` 重跑同一份备份的隔离恢复，不产生新备份。
2. 在新项目目录恢复 `settings/` 下的配置、密钥、Compose和Caddy文件。恢复源码包并重建相应镜像；确认镜像、公开URL、issuer、回调、数据库密码及卷名均属于目标项目。更换主机需先确认SSH指纹和客户端CA信任。
3. 创建全新数据库卷和应用/Caddy卷。用备份内数据库密码初始化临时管理员 `ba_restore`、数据库 `restore_control`，设置 `TZ=Asia/Shanghai`；以该管理员向空集群执行 `psql -v ON_ERROR_STOP=1 < cluster.sql`，恢复原数据库和角色。不要直接把SQL导入已有业务集群。
4. 将 `data.tar`、`caddy.tar`、`config.tar` 分别解到目标新卷并保留原属主/权限，挂载配套密钥。数据库恢复后启动迁移与五个服务，等待全部健康。
5. 核对两个角色的真实登录、会话及附件、数据库只读源、报告正文和双格式下载哈希。通过后再切换使用目标入口；失败时保留原卷和备份，回到原实例排查。

恢复演练验证了数据库、文件、密钥和只读连接；入口证书、真实OIDC和重启后报告下载在本次交付实例另外验证。不要用 `docker compose down -v` 排查启动失败。
